# VLA Models and Emerging Physical AI Directions for a Single Franka Research 3 + Eye-in-Hand RGB-D Setup

Context for the report-writer: target hardware is a single Franka Research 3 arm (ROS2 Humble + MoveIt2, Franka Hand gripper), one wrist-mounted eye-in-hand RGB-D camera, two pick/place trays, and an already-working classical CV pipeline (solvePnP camera calibration, object detection, MoveIt2 planning, gripper grasp control — all verified on real hardware). Excluded directions (already covered by other researchers): plain VLA-only deep dive is IN scope (Part 1), but Active Perception, Closed-loop Manipulation, Failure-aware Manipulation, and Imitation Learning/Diffusion Policy are explicitly OUT of scope for Part 2 scouting.

## KQ1 (VLA): 2-3 representative VLA papers (title, authors, venue, year, core idea, open-source availability, compute requirements)

### Takeaway
Three representative, verifiably-sourced 2025 VLA systems span the spectrum from "foundation-model scale" to "fits on a workstation GPU": π0 / π0.5 (Physical Intelligence, flow-matching VLA, needs ≥70GB for full fine-tune but only ≥8GB for inference), OpenVLA (Stanford/Berkeley et al., 7B, 2024 paper but the dominant 2025 fine-tuning baseline, LoRA-tunable on a single high-memory GPU), and SmolVLA (Hugging Face/LeRobot, 2025, 450M params, explicitly designed to train on one consumer GPU or even a MacBook). A fourth, Evo-1 (Nov 2025), is also notable as a 2025-native "lightweight VLA" entrant.

### Cited Findings
- **π0 / π0.5**: Physical Intelligence released π0 weights and code on Feb 4, 2025, plus π0-FAST (autoregressive, FAST action tokenizer) — [Physical Intelligence blog](https://physicalintelligence.company/blog); the π0.5 paper, "π0.5: a Vision-Language-Action Model with Open-World Generalization," was posted to arXiv April 22, 2025 (arXiv:2504.16054) and trains on heterogeneous data sources for open-world generalization — [arXiv:2504.16054](https://arxiv.org/abs/2504.16054). π0.5 is also listed as a CoRL 2025 paper — [roboticscenter.ai guide](https://www.roboticscenter.ai/guides/vla-models-comparison).
- **π0/π0.5 compute**: per the official `openpi` repo's requirements table — inference needs >8GB GPU memory (example: RTX 4090); LoRA fine-tuning needs >22.5GB (RTX 4090); full fine-tuning needs >70GB (A100-80GB or H100). Multi-GPU is possible via `fsdp_devices`, but multi-node training is not yet supported — [github.com/Physical-Intelligence/openpi](https://github.com/Physical-Intelligence/openpi).
- **π0/π0.5 architecture/robots**: openpi documents DROID (Franka-based), ALOHA (real + sim), and UR5 platforms, with checkpoints for DROID and ALOHA; the DROID inference example explicitly uses a `observation/wrist_image_left` key, confirming wrist/eye-in-hand camera input is a supported observation modality — [github.com/Physical-Intelligence/openpi](https://github.com/Physical-Intelligence/openpi). Secondary sources estimate π0 at ~3.3B parameters (3B VLM + ~300M action expert, 50-step action chunks up to 50Hz), though this figure is from blog sources, not the primary paper — [roboticscenter.ai](https://www.roboticscenter.ai/guides/vla-models-comparison).
- **π0/π0.5 license**: code is Apache-2.0; weights are hosted on Google Cloud Storage and auto-downloaded/cached, with no separately stated weight license noted on the repo page — [github.com/Physical-Intelligence/openpi](https://github.com/Physical-Intelligence/openpi).
- **OpenVLA**: "OpenVLA: An Open-Source Vision-Language-Action Model" is a 7B-parameter open VLA trained on 970k real-world robot demonstrations, and the paper reports it beats RT-2-X (55B) by 16.5 points across 29 tasks with 7x fewer parameters — [arXiv:2406.09246](https://arxiv.org/pdf/2406.09246). (Note: OpenVLA itself is a 2024 paper, but it remains the dominant 2025 baseline/backbone for fine-tuning studies and comparisons, so it is included as essential context per the task's allowance for brief older context.)
- **OpenVLA fine-tuning compute**: the paper states LoRA can adapt OpenVLA to a new task within 10-15 hours on a single A100 GPU, training only ~1.4% of parameters while matching full fine-tuning performance — [arXiv:2406.09246](https://arxiv.org/pdf/2406.09246). A DigitalOcean tutorial claims LoRA fine-tuning is possible on a single 24GB consumer GPU, though this is described as a general VLA claim, not verified specifically for OpenVLA — [DigitalOcean tutorial](https://digitalocean.com/community/tutorials/vision-language-action-finetuning-robotics). An AWS blog demonstrates OpenVLA LoRA fine-tuning on SageMaker with 4x L40S (48GB each) as sufficient — [AWS Physical AI blog](https://aws.amazon.com/blogs/physical-ai/fine-tuning-openvla-on-amazon-sagemaker-ai-with-lora/). Secondary comparison sources disagree on exact VRAM figures (one cites ~72GB for LoRA at batch size 16, another ~16GB BF16), reflecting batch-size/precision differences rather than a settled number — [roboticscenter.ai](https://www.roboticscenter.ai/guides/vla-models-comparison).
- **OpenVLA original training cost**: one secondary survey reports the base OpenVLA model itself was originally trained on 64 A100 GPUs for ~14 days — [roboticscenter.ai](https://www.roboticscenter.ai/guides/vla-models-comparison) — i.e., pretraining from scratch is a cluster-scale task; only fine-tuning an existing checkpoint is single-GPU-realistic.
- **SmolVLA**: Hugging Face/LeRobot's SmolVLA (2025) is a ~450M-parameter model (action expert ~100M) pretrained only on 487 curated open-source community LeRobot datasets (~10M frames, <30k episodes), explicitly described as "small enough to run on CPU, train on a single consumer GPU, or even a MacBook" — [huggingface.co/blog/smolvla](https://huggingface.co/blog/smolvla). It was evaluated on real SO100/SO101 arms for pick-place, stacking, and sorting, and the dataset camera convention standardizes a wrist-mounted view (`OBS_IMAGE_2`) alongside a top-down view, implying eye-in-hand input is natively supported by its data format — [huggingface.co/blog/smolvla](https://huggingface.co/blog/smolvla). Base weights are public on the Hub (`lerobot/smolvla_base`) and code is in the LeRobot GitHub repo; the blog post does not state an explicit license.
- **Evo-1** (arXiv 2511.04555, Nov 2025): "Evo-1: Lightweight Vision-Language-Action Model with Preserved Semantic Alignment" builds on a native multimodal VLM with a diffusion transformer action head, explicitly targeting low-cost training and high-efficiency inference on consumer-grade GPUs; the authors released code, data, and weights — [arXiv:2511.04555](https://arxiv.org/html/2511.04555v1).
- **NanoVLA** (arXiv 2510.25122, Oct 2025): "NanoVLA: Routing Decoupled Vision-Language Understanding for Nano-sized Generalist Robotic Policies" keeps vision and language processing decoupled until late in the pipeline, reducing per-frame compute for very small policies — [arXiv:2510.25122](https://arxiv.org/html/2510.25122v1).

### Inferences
- There is a clear bimodal split in the 2025 VLA landscape: "foundation-scale" systems (π0/π0.5, OpenVLA pretraining, RT-2/RT-2-X) that require multi-GPU clusters (8-64 A100/H100-class GPUs) to train from scratch, versus a fast-growing 2025 wave of "small VLA" systems (SmolVLA, Evo-1, NanoVLA, TinyVLA) explicitly engineered for single consumer/workstation GPU training and CPU-feasible inference.
- For a single Franka + eye-in-hand setup, the realistic path is not training a VLA from scratch, but either (a) LoRA/PEFT fine-tuning an existing mid-size checkpoint (OpenVLA 7B via LoRA, or π0/π0.5 via LoRA at the >22.5GB tier) on a single high-memory workstation GPU (e.g., RTX 4090/A6000, 24-48GB), or (b) adopting a small, 2025-native model (SmolVLA 450M, Evo-1) that was designed for exactly this compute envelope and already supports wrist-camera-style observations.

### Gaps
- No primary-source parameter count or detailed compute table was found directly in the π0.5 arXiv paper abstract itself (figures are cross-referenced from openpi repo and secondary blog sources); a full read of arXiv:2504.16054 would be needed to confirm π0.5's exact parameter count and whether it differs from π0.
- RT-2 / RT-2-X (Google DeepMind) is included only as brief foundational context per secondary sources (55B PaLI-X-based, or an inconsistently-cited 12B PaLM-E variant); it is not open-source/weights-released, and inference latency is reported as "measured in seconds — too slow for reactive control" per a secondary comparison guide, not a primary DeepMind source — [roboticscenter.ai](https://www.roboticscenter.ai/guides/vla-models-comparison). This should be treated as context only, not a verified primary claim.
- Exact minimum VRAM for OpenVLA LoRA fine-tuning is unresolved across sources (claims range from 16GB to 72GB depending on batch size/precision); no single authoritative number was found.

## KQ2 (VLA): Is there a lightweight/fine-tunable VLA variant realistic to deploy on a single Franka + eye-in-hand RGB-D with modest compute?

### Takeaway
Yes — SmolVLA (450M params, single consumer GPU, CPU-capable inference, native wrist-camera data convention) is the most realistic lightweight/fine-tunable candidate currently documented with explicit compute claims; Evo-1 and NanoVLA are 2025-native alternatives aimed at the same consumer-GPU envelope but with less documentation found in this research pass. For mid-size models, OpenVLA (7B) via LoRA on a single A100-class (or possibly 24GB-tier) GPU, or π0/π0.5 via LoRA at the ≥22.5GB tier, are realistic "one workstation GPU" fine-tuning paths, as opposed to the ≥70GB full-fine-tune tier which is effectively cluster/A100-80GB-class and not single-consumer-GPU realistic.

### Cited Findings
- SmolVLA is explicitly marketed and evaluated for "train on a single consumer GPU, or even a MacBook," pretrained on real low-cost arms (SO100/SO101, also compatible with LeKiwi), with real pick-place/stacking/sorting task evaluation — [huggingface.co/blog/smolvla](https://huggingface.co/blog/smolvla).
- OpenVLA LoRA fine-tuning is documented at "10-15 hours on a single A100 GPU," training ~1.4% of parameters — [arXiv:2406.09246](https://arxiv.org/pdf/2406.09246) — which is a single-GPU (if high-memory) workstation-realistic budget, distinct from the 64-A100/14-day pretraining cost of the base model.
- π0/π0.5 LoRA fine-tuning requires >22.5GB (e.g., one RTX 4090), per the official openpi repo requirements table, making it borderline-feasible on a single well-equipped workstation GPU, while full fine-tuning (>70GB) is not — [github.com/Physical-Intelligence/openpi](https://github.com/Physical-Intelligence/openpi).
- No source in this research pass explicitly confirms a Franka Research 3 + eye-in-hand RGB-D deployment of SmolVLA, Evo-1, or NanoVLA; the closest confirmed Franka-adjacent VLA deployment found is π0's support for the "DROID Franka setup" with wrist-camera observation keys — [github.com/Physical-Intelligence/openpi](https://github.com/Physical-Intelligence/openpi).

### Inferences
- SmolVLA is the best-documented "realistic, modest-compute" VLA starting point for this exact hardware class, though it was validated on low-cost arms (SO100/SO101), not Franka — a researcher would need to collect Franka-specific demonstration data (teleop or scripted) and fine-tune, which the classical pipeline's existing calibration/grasp pipeline could help bootstrap (see KQ5).
- If the research priority is staying closest to the "serious" CoRL/RSS-grade VLA literature rather than the smallest possible model, OpenVLA-via-LoRA on a single A100 (or π0/π0.5-via-LoRA on a single ≥24GB GPU) is the more defensible middle ground, trading more GPU memory for a more mainstream, heavily-cited backbone.

### Gaps
- No RGB-D-specific (depth-channel) VLA variant was identified in this pass — all three main candidates (π0, OpenVLA, SmolVLA) appear to consume RGB images only; how to incorporate the wrist camera's depth channel (beyond using it only for the classical pipeline's solvePnP/coordinate transform) is an open implementation question, not answered by current literature found here.
- No direct report of SmolVLA, Evo-1, or NanoVLA running specifically on a Franka Research 3 was found; this is inferred compatibility (via LeRobot's general framework support), not a confirmed deployment.

## KQ3 (Broader scouting): 1-3 additional directions most promising for this hardware, with justification and example papers

### Takeaway
Three directions stand out as unusually well-matched to this exact hardware (single arm, single eye-in-hand RGB-D, accurate classical calibration, two trays): (1) **3D Gaussian Splatting (3DGS) / Gaussian-Splatting digital twins for sim-to-real and collision-aware planning**, which directly extends the existing solvePnP-calibrated camera and MoveIt2 planning stack; (2) **zero-shot / foundation-model-based grasp affordance reasoning**, which can bolt onto the existing object-detection step without requiring any new hardware or large training runs; and (3) **learned world models for manipulation**, a strong 2025 CoRL trend but a harder fit given the single eye-in-hand (no third-person) camera. Tactile sensing integration is a well-represented CoRL 2025 trend but is a weaker fit here since it requires new sensor hardware (the stock Franka Hand has no tactile skin).

### Cited Findings
- **3DGS for manipulation/digital twins**: "A High-Fidelity Digital Twin for Robotic Manipulation Based on 3D Gaussian Splatting" (Sun, Bao, Peng, Sun, Zhou; arXiv:2601.03200, posted Jan 2026, under review at Journal of Robot Learning) uses 3DGS for fast photorealistic reconstruction, then applies opacity thresholding, scale-based filtering, and DBSCAN clustering to convert the splat point cloud into collision meshes for planning, validated on a **Franka Emika Panda doing pick-and-place** with a Unity-ROS2-MoveIt stack, reporting that motion plans built from the converted collision geometry transferred to real execution — [arXiv:2601.03200](https://arxiv.org/pdf/2601.03200). A related paper, GaussTwin (arXiv:2603.05108, March 2026), reportedly also targets Gaussian-splatting digital twins specifically on a **Franka Research 3** — [search result listing, arXiv:2603.05108](https://arxiv.org/abs/2603.05108) (title/abstract not independently fetched/verified in this pass).
- **3DGS for sim-to-real training data**: RoboSimGS (arXiv:2510.10637, Oct 2025) uses a hybrid 3DGS (appearance) + mesh (physics) Real2Sim2Real framework; policies trained only on the resulting synthetic data reportedly transferred zero-shot to real-world tasks — [arXiv:2510.10637](https://arxiv.org/abs/2510.10637). SplatSim (CMU, 2025) uses Gaussian Splatting as the primary rendering primitive specifically to reduce the sim-to-real gap for RGB-based manipulation policies — [CMU MSR thesis](https://www.ri.cmu.edu/app/uploads/2025/08/cmu_msr_thesis_master-5.pdf).
- **Grasp affordance foundation models**: ORACLE-Grasp (arXiv:2505.08417, 2025) uses an existing general-purpose large multimodal model with chain-of-thought prompting for affordance-aligned grasping, requiring "no data collection, dataset curation or pretraining, operating in a fully zero-shot manner," with reported real-robot pick-up success on novel objects — [arXiv:2505.08417](https://arxiv.org/pdf/2505.08417). OVAL-Grasp (arXiv:2511.20841, Nov 2025, presented at ISER 2025) is a zero-shot open-vocabulary task-oriented grasping pipeline: an LLM splits objects into "grasp" vs. "avoid" parts, a vision-language segmentation model localizes those parts, and a grasp-proposal model selects the grasp; evaluated on YCB objects against GraspGPT and ShapeGrasp baselines — [arXiv:2511.20841](https://arxiv.org/pdf/2511.20841).
- **World models for manipulation**: LaDi-WM (CoRL 2025) uses a latent diffusion world model to imagine future states from an initial policy action sequence, refining actions before execution, with reported gains in both simulation and real-world tests — [arXiv:2505.11528](https://arxiv.org/html/2505.11528v3). RoDyn models manipulation dynamics in a "geometry-aware 2.5D latent space" (depth + mask prediction conditioned on robot actions), arguing common 2D video world models "lack the spatial and kinematic reasoning needed for physical interaction" — [arXiv:2510.09036](https://arxiv.org/pdf/2510.09036). A 2025 survey frames world models as internal representations supporting prediction and planning across perception/prediction/control — [arXiv:2511.02097](https://arxiv.org/html/2511.02097v1).
- **Tactile sensing (context, weaker fit)**: VT-Refine (CoRL 2025, Seoul) targets bimanual visuo-tactile assembly using piezoresistive pads and GPU-parallelized tactile simulation; DexSkin (CoRL 2025) is a soft capacitive electronic skin for robot fingers enabling contact-rich manipulation policies; "Tactile Beyond Pixels" (Higuera et al., CoRL 2025) covers multisensory touch representations — [cs.cmu.edu citation page](https://www.cs.cmu.edu/~kaess/pub/Higuera25corl.html). A 2025 survey notes current robot foundation models focus mainly on vision/position control, with force/tactile sensing still an active gap — [arXiv:2504.11827](https://arxiv.org/html/2504.11827).
- **General 2025 conference context**: An (unverified, non-peer-reviewed) ICRA 2025 recap blog reports ICRA 2025 was the most selective ever (~35% acceptance) — [itcanthink.substack.com](https://itcanthink.substack.com/p/icra-2025-was-bigger-and-more-serious). Two late-2025 surveys (arXiv:2512.22983 and arXiv:2510.10903) organize foundation-model-era manipulation research around planning/learning perspectives and identify prospective future directions — [arXiv:2512.22983](https://arxiv.org/html/2512.22983), [arXiv:2510.10903](https://arxiv.org/abs/2510.10903v1).

### Inferences
- The 3DGS/digital-twin direction is unusually well-matched to this exact hardware because the lab already has a verified solvePnP camera calibration and MoveIt2 planning pipeline — the Sun et al. (arXiv:2601.03200) pipeline is structurally almost identical (3D reconstruction → collision mesh → MoveIt planning → real Franka execution), meaning the new research contribution would be swapping their generic reconstruction step for the lab's already-calibrated wrist camera, directly reusing existing calibration accuracy as a foundation rather than rebuilding it.
- Grasp-affordance foundation models are the lowest-friction addition: they slot in as a drop-in replacement/supplement for the "object detection" stage of the existing classical pipeline (feeding a VLM-derived grasp region into the already-working solvePnP-to-robot-frame transform and MoveIt2 grasp execution), requiring no new training infrastructure and no new sensors.
- World models are a strong 2025-2026 CoRL trend but are a comparatively harder fit for a single eye-in-hand-only camera setup, since most published world-model work (LaDi-WM, RoDyn) assumes richer or multi-view observation streams and is evaluated on relatively long-horizon/dynamic tasks; adapting them to pick-and-place off two static trays is possible but would require more novel adaptation work than the other two directions.
- Tactile sensing is a legitimate, fast-growing CoRL 2025 trend, but given the "Franka Hand gripper" is the stock Franka Hand (no stated tactile upgrade), this direction would require new sensor procurement/integration before any software contribution — a materially bigger lift than the vision-only directions.

### Gaps
- GaussTwin (arXiv:2603.05108) was only seen in a search-result title/abstract snippet, not independently fetched and verified for its Franka Research 3 claim; this should be flagged to the report-writer as needing a follow-up primary-source check if it is cited as confirmed.
- No direct evidence was found of any of the three recommended directions (3DGS digital twin, grasp-affordance foundation models, world models) having been evaluated specifically with a wrist-mounted eye-in-hand RGB-D camera (as opposed to a third-person/external camera) — most papers found use externally-mounted or multi-view camera rigs. This is a genuine gap the lab's setup would need to navigate (addressed partially in KQ5).
- No official CoRL 2025 / ICRA 2025 / RSS 2025 accepted-papers list was directly retrieved (only an unofficial GitHub mirror and papers.cool venue page were found); paper-count/trend-share statistics (e.g., "X% of CoRL 2025 papers were about world models") could not be obtained and are not claimed here.

## KQ4: Estimated implementation difficulty and development time for each candidate, building on the existing classical pipeline

### Takeaway
Ranked roughly from easiest to hardest for a single researcher building on an already-working classical pipeline: grasp-affordance foundation model integration (weeks, low-moderate difficulty) < SmolVLA fine-tuning (weeks-to-~1-2 months, moderate difficulty) < 3DGS digital-twin/sim-to-real (1-3 months, moderate-high difficulty, mostly engineering) < OpenVLA/π0 LoRA fine-tuning (1-2 months but GPU-access-gated, moderate-high difficulty) < world-model-based planning (2-4+ months, high difficulty, most novel-adaptation work required). These are inferred engineering estimates, not sourced from any paper's stated timeline, since no source in this research pass reported development-time figures.

### Cited Findings
- No paper found in this research pass reports a "single researcher development time" figure; all difficulty/time estimates below are inferences from documented compute/training requirements, not direct citations.
- Supporting compute facts used for these inferences: OpenVLA LoRA fine-tuning is reported at 10-15 hours of GPU time on a single A100 — [arXiv:2406.09246](https://arxiv.org/pdf/2406.09246); SmolVLA fine-tuning example uses batch size 64 for 20,000 steps and is designed to run on a single consumer GPU — [huggingface.co/blog/smolvla](https://huggingface.co/blog/smolvla); π0/π0.5 LoRA fine-tuning requires >22.5GB GPU memory per the openpi repo — [github.com/Physical-Intelligence/openpi](https://github.com/Physical-Intelligence/openpi); ORACLE-Grasp requires no data collection or pretraining at all, operating fully zero-shot by calling an existing LMM — [arXiv:2505.08417](https://arxiv.org/pdf/2505.08417).

### Inferences
- **Grasp-affordance foundation models (e.g., ORACLE-Grasp/OVAL-Grasp style)**: Lowest difficulty/fastest — since these papers explicitly require "no data collection, dataset curation or pretraining," the main engineering work is prompting/API integration (or running an open VLM locally) and wiring its output region/point into the existing solvePnP-based pixel-to-robot-frame transform already built and verified. Estimated 2-6 weeks for a working integrated demo, since the hardest parts (calibration, motion planning, gripper control) already exist.
- **SmolVLA fine-tuning**: Moderate difficulty — requires collecting a Franka-specific teleop/demo dataset (likely the dominant time cost, not the model training itself, which fits on a consumer GPU per its own documentation), converting to LeRobot dataset format, and fine-tuning. Estimated 4-8 weeks, dominated by demonstration collection and sim/real debugging rather than compute.
- **3DGS digital-twin / sim-to-real**: Moderate-to-high difficulty — the Sun et al. (arXiv:2601.03200) pipeline shows the approach is reproducible (3DGS capture → mesh conversion → MoveIt planning), but building a robust capture rig (multiple wrist-camera viewpoints or an auxiliary scanning pass), tuning the opacity/DBSCAN mesh-conversion parameters, and validating sim-to-real transfer is substantial systems-integration work. Estimated 6-12 weeks for a single researcher, mostly engineering rather than novel algorithm design (which is favorable for a "build on existing pipeline" project).
- **OpenVLA or π0/π0.5 LoRA fine-tuning**: Moderate-to-high difficulty, primarily gated by GPU access (need a single ≥24-80GB GPU reliably available) rather than algorithmic difficulty, since LoRA recipes are documented and open-source. Estimated 4-8 weeks assuming GPU access is already available; add significant delay if the lab must acquire/rent such a GPU.
- **World-model-based planning (LaDi-WM/RoDyn-style)**: Highest difficulty — these are recent (2025) research-grade systems without the maturity/tooling of OpenVLA or LeRobot, and adapting them to a single eye-in-hand camera (most were demonstrated with richer observation setups) would itself be a research contribution, not just an integration task. Estimated 2-4+ months, with higher risk of not reaching a working real-robot demo in that time.

### Gaps
- All time estimates above are this researcher's engineering inference based on documented compute/data requirements, explicitly not sourced from any paper or benchmark — no source reports actual single-researcher development timelines for any of these systems. The report-writer should present these as estimates, not cited facts.

## KQ5: Where is there room for genuine NEW research contribution combining VLA or a scouted direction with the existing classical pipeline?

### Takeaway
The clearest, well-justified novel-contribution angles are: (1) using the classical pipeline's solvePnP-calibrated, verified-accurate object pose as ground truth to quantitatively benchmark a learned policy's (VLA or affordance-model) real-world pose/grasp accuracy — a measurement capability most VLA papers lack since they rely on task success rate, not metric pose error; (2) using the classical pipeline as an initial-pose proposer that a learned model refines (e.g., affordance model picks the object/region, classical solvePnP gives a coarse 6-DoF estimate, a small learned residual model corrects for calibration drift or occlusion-induced error); and (3) using the classical pipeline as a safety/fallback monitor that intervenes when a learned policy's uncertainty or divergence from the geometrically-verified estimate is high. These map directly onto the user's own suggested angles and are not contradicted by anything found in this research pass — but no source paper in this research pass was found that performs exactly this combination, so this is an identified gap/opportunity rather than a reproduction of existing work.

### Cited Findings
- No paper found in this research pass explicitly combines a classical solvePnP-calibrated pipeline with a VLA or grasp-affordance foundation model in the ground-truth/fallback/proposer role described above; the closest structural analogue found is the Sun et al. 3DGS digital twin paper, which uses a classical-style collision-mesh-to-MoveIt pipeline but as the primary planner, not as a secondary ground-truth/fallback layer for a learned policy — [arXiv:2601.03200](https://arxiv.org/pdf/2601.03200).
- Grasp-affordance papers like ORACLE-Grasp and OVAL-Grasp evaluate success purely via real-robot pick-up success rate on novel objects, not via metric comparison to a geometrically-calibrated ground truth pose — [arXiv:2505.08417](https://arxiv.org/pdf/2505.08417), [arXiv:2511.20841](https://arxiv.org/pdf/2511.20841) — meaning a contribution that adds rigorous, calibration-grounded quantitative pose-error evaluation would be a methodological novelty relative to current practice in this sub-area.
- The forceful-robotic-foundation-models survey explicitly states that "current robot foundation models focus mainly on vision and position control" and treats force/tactile integration as an open gap — [arXiv:2504.11827](https://arxiv.org/html/2504.11827) — supporting that foundation-model-plus-classical-sensing combinations remain under-explored broadly, not just for this specific hardware.

### Inferences
- **Ground-truth evaluation angle**: Because the classical pipeline's solvePnP calibration is already verified on real hardware, it can serve as a trusted "oracle" for 6-DoF object pose. A genuinely new contribution is building an evaluation harness that runs a fine-tuned small VLA (e.g., SmolVLA) or a grasp-affordance model (e.g., ORACLE-Grasp-style) side-by-side with the classical pipeline on the same scene, and reports metric pose/grasp-point error against the calibrated ground truth — not just task success/failure. This is a measurable, publishable gap since current VLA/affordance papers (per findings above) report only task success rates.
- **Initial-pose-proposer / residual-refinement angle**: A new contribution could use the classical detection+solvePnP stage to produce a fast, interpretable coarse pose estimate, and train a small learned refinement model (could be a lightweight VLA action head or a dedicated regression network) to correct residual error from lighting, partial occlusion, or novel object geometry that the classical pipeline struggles with — framing the learned component as a narrow, data-efficient add-on rather than a full end-to-end replacement. This directly addresses the "modest compute, single researcher" constraint, since the learned model only needs to learn a correction, not full perception-to-action mapping.
- **Safety fallback / uncertainty-gated handoff angle**: A new contribution could define a confidence/divergence metric between a learned policy's (VLA or affordance model) proposed action and the classical pipeline's geometrically-verified estimate, and trigger a fallback to the classical pipeline when divergence exceeds a threshold — directly useful for a single-arm real-hardware lab setting where safety and reliability during experiments matter, and currently under-addressed in the VLA literature surveyed here (none of the found papers describe a classical-geometric-fallback mechanism).
- Of the three angles, the ground-truth-evaluation angle is likely the fastest to execute (it requires no new training, only an evaluation harness) and could be combined with either the grasp-affordance direction or a fine-tuned SmolVLA, making it a good first milestone before attempting the more ambitious residual-refinement or safety-fallback contributions.

### Gaps
- No existing paper combining classical geometric calibration with a learned VLA/affordance model in any of these three roles was found in this research pass — this strengthens the case that it is a genuine open contribution, but it also means there is no directly analogous prior-art baseline to benchmark against; the researcher would likely need to establish their own baseline/metric protocol from scratch.
- It remains unverified whether any 2025-2026 paper has specifically used calibration accuracy (e.g., solvePnP reprojection error) as a formal uncertainty/trust signal for gating between a learned and classical manipulation pipeline; this specific framing was not found in the sources retrieved and should be flagged as a novelty claim pending a more targeted literature check before publication.
